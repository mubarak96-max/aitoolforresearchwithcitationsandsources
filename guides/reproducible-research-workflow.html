Reproducible research: a workflow you can start this week

Six months from now, someone will ask how you got a number in Table 3. It might be an examiner, a reviewer or you. A reproducible workflow means the answer is “run this script” rather than a weekend of archaeology.

By the Methods & Sources editorial teamUpdated 14 November 20267 min read
Short answer Research is reproducible when someone else can take your data and code and get the same results. To get there: keep raw data read-only; do every cleaning and analysis step in scripts, not by hand; use version control; record your software environment; write a README and data dictionary; and share data and code in a repository that gives a DOI. Start with the folder structure and the scripts; the rest builds on them.

Reproducible, replicable, robust

The words are used loosely, so it helps to pin them down. A common set of definitions, used by The Turing Way community handbook, is:

Same dataDifferent data
Same analysisReproducibleReplicable
Different analysisRobustGeneralisable

Reproducibility is the minimum. It does not prove a finding is true, but if your own results cannot be regenerated from your own data, nothing else can be checked. The free, community-written Turing Way handbook covers every step below in more depth.

Step 1: a folder structure that explains itself

Use the same layout for every project, so you and collaborators always know where things live:

project-name/
├── README.md          what this is, how to run it
├── data/
│   ├── raw/           original files, never edited
│   └── processed/     created by scripts only
├── code/
│   ├── 01_clean.R
│   ├── 02_analyse.R
│   └── 03_figures.R
├── outputs/
│   ├── figures/
│   └── tables/
├── docs/              protocol, data dictionary, ethics
└── manuscript/

Number the scripts in the order they run. Anything in processed/ or outputs/ should be deletable and recreated by running the scripts in order. If deleting it would lose work, that work is not yet reproducible.

Step 2: treat raw data as read-only

  • Save the original export from your survey platform, instrument or database in data/raw/ and never edit it. Set the files to read-only if you can.
  • Record where each raw file came from and when: the export date, the query used, the instrument settings.
  • Do every correction in code, with a comment explaining why: # participant 017 entered age as 250; set to missing (see notes 2026-03-02).
  • Keep identifiable data separate and protected, as your ethics approval requires. Share only de-identified versions.

Step 3: script every step

Pointing and clicking in a spreadsheet or menu-driven statistics package leaves no record. Scripts are the record. Use R, Python, Stata or SPSS syntax, whichever your field uses, and follow a few habits:

  1. One script, one job: cleaning, analysis and figures in separate files.
  2. Relative paths only (data/raw/survey.csv, not C:/Users/me/Desktop/…), so the project runs on any computer.
  3. Set a random seed before any step involving randomness, such as bootstrapping, multiple imputation, cross-validation or simulation.
  4. Generate tables and figures from code, then insert them into the manuscript. Never retype a number.
  5. Consider literate programming with Quarto, R Markdown or Jupyter notebooks, which mix text and code so the report regenerates when the data changes.

Already analysed in a menu-driven package? Most can show or paste the syntax for what you clicked. Save that syntax in code/ now; it is far better than nothing.

Step 4: use version control

Version control (almost always Git) records every change to your code and text, with a message saying why. It replaces files named analysis_final_v3_REAL.R. You can see exactly what changed between the version you sent your supervisor and today, and you can go back if something breaks.

  • Commit small, logical changes with clear messages: “Exclude incomplete responses (<80% items)”.
  • Do not commit large raw data files or anything identifiable. List them in a .gitignore file.
  • Tag the commit used for each submission, for example v1-submitted and v2-revision, so the numbers in each version of the paper can be traced.

Step 5: record the software environment

Code that runs today may not run in two years, when packages have changed. Record what you used:

  • R: use renv to save package versions with the project, and include sessionInfo() output.
  • Python: save a requirements.txt or an environment file with pinned versions.
  • Anything else: note the software name and version in the README and the methods section.

For complex pipelines, containers such as Docker capture the whole system, but for most theses a package lockfile and version notes are enough.

Step 6: document for a stranger

Write for someone who has never seen the project, because that is who future-you will be.

  • README: what the project is, how to run the scripts in order, and what each output is.
  • Data dictionary: every variable’s name, label, type, units, allowed values and missing-value codes.
  • Analysis plan or protocol in docs/, with any changes dated and explained.
  • Licence: state how others may reuse the code (for example MIT) and data (for example CC BY 4.0).

Step 7: preregister when it fits

Preregistration means recording your hypotheses, design and analysis plan before you see the outcome data. It separates confirmatory tests from exploratory ones and protects you against accusations of fishing for results. Free registries include the Center for Open Science’s OSF for most fields, PROSPERO for health-related systematic reviews, and clinical trial registries for trials. Deviations are fine; report them openly. Our research proposal guide shows how to write the analysis plan you would register.

Step 8: share data and code with a DOI

A link to a personal website breaks. A repository with a persistent identifier does not. General-purpose options include Zenodo (run by CERN) and OSF, and many universities and fields have their own repositories. A DOI for your dataset lets others cite it, and lets you list it as a research output.

Aim for data that meets the FAIR principles: Findable (a DOI and good metadata), Accessible (clear access conditions, even if access is restricted), Interoperable (open formats such as CSV rather than proprietary ones) and Reusable (a licence and a data dictionary). When data cannot be shared because of consent or privacy, share the code, a synthetic or minimal dataset, and the process for requesting access.

What about qualitative research?

Reproducibility in the computational sense, rerunning code for the same numbers, does not translate directly to interviews and ethnography, where interpretation is the method. The underlying goal, letting others see how you got from data to findings, still applies. The equivalents are:

  • A versioned codebook with definitions, inclusion rules and an example quote for each code, dated each time it changes.
  • An audit trail: memos recording analytic decisions, such as why two codes were merged or a theme was dropped.
  • Raw transcripts kept unedited, with de-identified working copies, just like raw quantitative data.
  • A reflexivity statement describing your position relative to the participants and topic.
  • Reporting against a guideline such as COREQ or SRQR, so readers can see what was done.

Sharing qualitative data is harder because of consent and re-identification risk. Plan it at the ethics stage: if participants agree, specialist archives can hold transcripts under controlled access.

Where to start if you are mid-project

You do not need to rebuild everything. In order of value:

  1. Copy your original data into data/raw/ and stop editing it.
  2. Turn the cleaning you did by hand into a script, even an imperfect one.
  3. Make the script produce your main table, and check it matches the draft.
  4. Put the folder under Git and write a ten-line README.
  5. Before submission, run everything from scratch on a clean copy, ideally on someone else’s computer.

That last check catches most problems. For the statistical side of the write-up, see our guides to p-values and confidence intervals and effect sizes; for planning a whole doctorate around good habits, see the PhD research toolkit.

Frequently asked questions

What is reproducible research?

Research is reproducible when another person can take the same data and the same code or analysis steps and obtain the same results. It is the minimum standard for checking a finding, and it is different from replication, which repeats the study with new data.

What is the difference between reproducibility and replicability?

Reproducibility means getting the same results from the same data and analysis. Replicability means getting consistent results when the study is repeated with new data. A study can be reproducible but fail to replicate.

Do I need to know programming to make my research reproducible?

It helps, but it is not essential. Menu-driven packages such as SPSS can save the syntax of what you clicked, and many tools export analyses as code. Keeping raw data unedited, documenting every step and sharing materials already make a large difference.

Where should I share my research data?

Use a repository that issues a persistent identifier such as a DOI, for example Zenodo, OSF, your university repository or a subject repository for your field. Check your funder’s and journal’s data policies, and share only de-identified data that your consent forms allow.

What are the FAIR data principles?

FAIR stands for Findable, Accessible, Interoperable and Reusable. In practice it means a persistent identifier and good metadata, clear access conditions, open file formats, and a licence and documentation so others can reuse the data.
